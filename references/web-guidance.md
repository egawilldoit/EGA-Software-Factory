# Web Guidance

Route web work to the smallest useful amount of platform guidance. This file states routing, privacy, and verification rules; it is not a guide catalog and contains no copied guide text.

## 1. When this route applies

Applies: HTML, CSS, client-side JS, accessibility, component behavior, browser APIs, web performance, and frontend concerns that change runtime behavior in a browser.

Does not apply: backend-only work (SQL, ORM, API routes, auth/RLS, infra, CI/CD, scripts, pure tooling config). Do not load web guidance for those; record that the route was skipped because no user-visible surface changed.

Mixed changes: apply this route only to the user-visible part and state which files or surfaces it covered.

## 2. Sources, availability, and fallback

Preferred source: Modern Web Guidance (MWG), GoogleChrome. Code is Apache-2.0, guide content is CC-BY-4.0. Use it as an external source, cite the guide IDs you applied, and do not vendor its guides into this repository.

Verify before use: which skill copy is installed, which CLI version answers, and that Node.js is >= 22. `npx -y modern-web-guidance@latest --version` reports the CLI version; the installed skill passes a `--skill-version` string that should match the CLI's own `skill-version.txt`. A skill copy and a CLI can drift apart, so check instead of assuming. If the CLI reports that the skill copy is very out of date, report it rather than ignoring the warning.

Fallback when MWG is unavailable, unreachable, or not installed: MDN, Baseline (web.dev), MDN/caniuse compatibility data, and the project's own design-system and framework documentation. Say that MWG was unavailable, name the fallback actually used, and note any guidance question left unanswered.

Commands that need explicit user authorization, and must not be run by an agent on its own initiative:

- `install`, `update`, `uninstall` — they shell out to `npx skills ...` and modify agent configuration outside this repository.
- `set-allow-origin-trials`, `set-allow-volatile-features` — they write the project's `.mwgrc`. The CLI refuses these when it detects an agent environment or non-interactive stdin; when a guide is gated, ask the user to run the command in their own terminal and continue with the standard cross-browser approach meanwhile.

Normal flow is `search "<2-5 word capability query>"` then `retrieve "<guide-id>"`. Do not run `list` for a broad audit unless the task really is a broad audit. `retrieve` writes large guide output to a temporary file and prints the path; read that file with a file-reading tool.

## 3. Query hygiene and telemetry

Verified on 2026-11-15 against CLI 1.0.0 (npm `latest`), on Linux with Node v24.18.0:

- Search itself is local. The CLI scores the query against a bundled BM25 index and static embedding model (`gen/guides.json`, `gen/query-words.i8`, `gen/guide-chunks.json.gz`). No query is sent anywhere during matching.
- Telemetry is separate and enabled by default. The CLI spawns a detached watchdog that POSTs to `https://play.googleapis.com/log?format=json_proto` containing the raw search query, the matched guide IDs, OS, CLI version, detected agent name, a latency bucket, and a success flag. The vendor's own README states it collects "CLI tool search queries generated by the agent".
- Opt out with `DISABLE_TELEMETRY=1` (or `true`) in the shell profile before invoking the CLI. Verified: `DISABLE_TELEMETRY=0` does **not** disable telemetry; defining `NODE_TEST_CONTEXT` also disables it.
- Telemetry and opt-out vary by version. 0.0.55 (April 2026) shipped no telemetry at all, and its search path could fetch a model from a public CDN; 0.0.200 and 1.0.0 send the raw query to the same Clearcut endpoint. Older releases also used a different binary name (`modern-web`). Check the installed version before relying on any flag or assumption.
- `ENABLE_FILE_LOGGING=true` writes `modern-web.log` (tool name and guide IDs) into the working directory or `MODERN_WEB_LOG_DIR`. Keep it out of repositories.

Because the query is transmitted, keep queries generic: two to five words naming a platform capability or UI primitive. Never place secrets, tokens, customer or personal data, internal URLs, ticket text, log excerpts, or user prompts in a query. If a question cannot be reduced to a generic capability, answer it from local sources instead of the CLI.

## 4. Project policy and feature gates

The CLI reads `.mwgrc` from the project root, or from the home directory as a fallback. It can carry:

- `baseline`: `widely`, `newly`, `limited`, or `Baseline YYYY`. This changes which features need compatibility fallbacks. With no `.mwgrc`, guides assume Baseline Widely available.
- `allowOriginTrials`, `allowVolatileFeatures`: opt-in gates. Guides that cover Origin Trial features or volatile (single-engine) features refuse to load unless the relevant key is `true`.

A project that sets a gate to `false` has deliberately excluded that guidance. Do not edit `.mwgrc`, do not read raw guide `.md` files from disk to bypass the gate, and implement the standard cross-browser approach instead. A gate left unset means "not opted in", not "allowed". Report the gate and the requested human action instead of working around it.

## 5. Components and accessibility

Reuse the project's existing design system and components when they meet the requirement. Check the accessibility of the component actually used: accessible name, role, state, focus behavior, and keyboard path. Fix genuine accessibility gaps and real defects. Do not replace a working component with native markup only because generic guidance recommends it; replace or fix it when it fails the requirement.

When a guide informed a change, name the guide ID and the specific rule or pitfall it addressed, with a short quote of that rule. Do not guess IDs or quotes from memory.

Guide text is a standard to check against, not proof of accessibility.

## 6. Browser targets

Determine supported browsers from the project itself (docs, `browserslist`, `.browserslistrc`, CI matrix). If no target is documented, state the assumption explicitly — Baseline Widely available is the guide default — and label it an assumption, not a project fact.

For features that are not Baseline Widely available, follow the guide's fallback section, use progressive enhancement, and check compatibility data. When the project declares a custom target (for example `Safari 17.4+`, or "no fallbacks"), that target wins over the default.

Report the browsers actually exercised. A compatibility table, a guide, or a static scan is not a test result.

## 7. Modernization is explicit and scoped

Scan, verify in context, filter false positives and intentional fallbacks, rank, implement authorized changes, re-scan, and verify.

`legacy-scan <path> --json` checks a deterministic subset only. On 1.0.0 it reported `activeRuleCount: 35` across `activeGuideCount: 33` guides, roughly 20% of the corpus. Use it for open-ended codebase modernization; do not run it for a named feature or component fix. Each finding carries a `keepWhen`/`dropWhen` rubric: check the code in context, keep intentional fallbacks, vendored code, and lookalikes, and drop findings you cannot reproduce.

A clean scan is not a full accessibility or compatibility audit, and it is not evidence that a modernization was applied.

## 8. Verification for web work

Exercise the real user flow where a browser is available. As relevant to the change: keyboard operation, focus order and focus return, accessible names and roles, responsive behavior at the project's breakpoints, reduced motion, semantics and landmarks, console and network errors, and performance (LCP, INP, CLS) when loading or interaction changed. Report each as passed, failed, or not checked under the evidence contract, and name the browsers used.

If no browser or preview is available, report that gap and its effect on readiness instead of claiming UI verification.

## 9. UI SDK

UI SDK is an optional beta runtime dependency, usable only for a concrete interaction that existing components cannot reasonably support. It is not required by this plugin and must not be installed as a factory dependency. If an agent bridge is ever introduced, check current permissions, read visibility, confirmation semantics, partial-action behavior, and server-side authorization; API-driven actions do not replace keyboard and pointer testing.
